当前系统是一个“以 BLE 采集为主链路、以 SD 持久化和 MQTT 上报为双输出、以队列隔离慢速 I/O”的嵌入式网关架构。

## 1. 总体分层

```text
┌─────────────────────────────────────────────────────────┐
│ 应用与运维层                                             │
│ app_main / LCD-Touch UI / 串口 cfg、sys、stress、ota      │
├─────────────────────────────────────────────────────────┤
│ 业务领域层                                               │
│ 设备过滤 / 广播生命周期识别 / 设备表 / 事件模型           │
├─────────────────────────────────────────────────────────┤
│ 基础服务层                                               │
│ CSV / SD / Outbox / Wi-Fi / SNTP / MQTT / OTA            │
├─────────────────────────────────────────────────────────┤
│ 平台适配层                                               │
│ ESP-IDF、FreeRTOS、NimBLE、FATFS、NVS、CoreS3 BSP、LVGL   │
├─────────────────────────────────────────────────────────┤
│ 硬件层                                                   │
│ ESP32-S3、BLE、Wi-Fi、microSD、LCD、Touch、USB Serial/JTAG│
└─────────────────────────────────────────────────────────┘
```

目录结构与职责对应：

| 目录 | 分层定位 | 主要职责 |
|---|---|---|
| `main/app/` | 应用层 | 启动编排、LCD、Touch 与 UI 状态呈现。 |
| `main/ble/` | BLE 接入层 | NimBLE 主动扫描、广播名称解析与过滤、扫描性能采样。 |
| `main/device/` | 业务领域层 | 128 台设备表、广播开始/结束识别、生命周期事件分发。 |
| `main/storage/` | 存储服务层 | SD 挂载、CSV 生命周期记录、持久化 Outbox。 |
| `main/network/` | 网络服务层 | Wi-Fi、SNTP、MQTT、JSON、QoS 1 确认、OTA。 |
| `main/config/` | 配置与运维层 | NVS 配置、串口 `cfg`、`sys`、压力测试命令。 |
| `components/system_diagnostics/` | 可复用基础组件 | 内存、任务、CPU 诊断能力。 |

## 2. 核心采集数据流

```text
BLE 广播包
  │
  ▼
ble_scanner / NimBLE 回调
  │  只做：解析名称、匹配 SM_ICM数字 / SM_ICD数字、复制报告
  │
  ▼  scan queue（192，PSRAM）
device_manager_task
  │  MAC 去重、设备表、开始/结束判定、生成 broadcast_id
  │
  ├──────────────► UI queue（32） ──► app_ui_task ──► LCD/LVGL
  │
  ├──────────────► capture queue（512，PSRAM） ──► csv_logger_task ──► SD CSV
  │
  └──────────────► upload queue（512，PSRAM） ──► publisher_task
                                                    │
                                                    ├─► SD Outbox
                                                    └─► MQTT QoS 1 ─► PUBACK
```

这条链路的关键是：**NimBLE 回调不直接操作 SD、MQTT 或 LVGL**。它只做非常短的过滤和入队操作，避免几十台设备同时广播时慢速 I/O 阻塞蓝牙接收。

## 3. 设备业务模型

`device_manager` 管理的是“本网关观测到的广播生命周期”，不是产品的全局在线/离线状态。

- 首次收到某 MAC 的有效广播：`BROADCAST_STARTED`
- 后续广播：刷新该设备的最后观测时间与 RSSI
- 有效扫描累计超过 `bcast_end_s` 未再收到广播：`BROADCAST_ENDED`
- 同一轮开始与结束使用相同 `broadcast_id`
- 设备身份使用 MAC；BLE `address_type` 不参与设备去重
- 最大登记容量：128 台；超出后拒绝并记录计数

业务纯逻辑拆在 `device_manager_core.*`、`device_filter.*` 等文件中，可脱离 ESP-IDF 做主机单元测试；任务、队列、计时和日志留在运行时模块中。

## 4. 存储与可靠上报设计

本地采集优先级高于网络：

```text
生命周期事件
  ├─ CSV：用于人工取卡追溯
  └─ Outbox：用于网络中断后的 MQTT 重传
```

- `csv_logger` 仅记录广播开始、广播结束及关键网关事件，不记录每个广播包。
- `Outbox` 先持久化广播事件，再按顺序 MQTT QoS 1 发布。
- 收到匹配 `PUBACK` 后才推进 Outbox 读取位置。
- 断网、Broker 重启、断电后允许重复投递；服务端按 `gateway_id + event_id` 去重。
- SD 不可用但 MQTT 可用时允许实时发送，但会标记为非持久化投递。
- SD 与 MQTT 都不可用时，明确累计 `unrecoverable` 丢失计数，而不是静默丢失。

健康心跳是低优先级数据：MQTT 在线时直接发送；断网时仅覆盖保存最新一条，避免心跳占满 SD。

## 5. 网络与 OTA 架构

```text
NVS 配置
  │
  ├─ Wi-Fi STA ─► SNTP ─► MQTT
  │                         │
  │                         ├─ 上行：broadcast / gateway_health
  │                         └─ 下行：单网关 OTA command
  │
  └─ HTTPS OTA Manifest ─► SHA-256 校验 ─► 非运行 OTA 分区
                                              │
                                              ▼
                                      重启 + 10 秒自检 + 确认/回滚
```

网络模块分工：

- `network_manager`：Wi-Fi STA 自动连接与重连。
- `time_service`：SNTP 校时，为 CSV 与 MQTT 提供绝对时间。
- `mqtt_service`：连接、发布、PUBACK、专属 OTA Topic 订阅。
- `gateway_publisher`：事件 JSON 编码、Outbox 调度、健康心跳。
- `ota_manager`：Manifest 获取、兼容性检查、下载、SHA-256、双分区切换、回滚确认。
- `ota_command`：处理网关专属 MQTT OTA 命令、到期校验、NVS 命令去重。

远程 OTA 命令路径为：

```text
MQTT mqtts://
  └─ factory/product-status/gateway/<gateway_id>/commands/ota
       └─ ota_command
            └─ ota_manager
                 └─ HTTPS Manifest + Firmware
```

远程命令仅接受 `mqtts://`、HTTPS Manifest、未过期且未重复的 `command_id`；最终镜像仍通过 HTTPS、SHA-256、硬件型号、芯片目标和分区布局校验。

## 6. 启动架构

入口为 [app_main.c](main/app/app_main.c)。

启动顺序体现“采集优先、网络可降级”：

1. 初始化 NVS。
2. 加载网关配置，启动串口配置与诊断命令。
3. 初始化时间服务、BLE 扫描器、设备管理器。
4. 启动 SD 存储管理与 CSV 记录任务。
5. 启动 LCD/Touch UI。
6. 启动 Wi-Fi、MQTT、发布器。
7. 启动 OTA 管理器与 OTA MQTT 命令模块。
8. 若当前镜像处于 OTA 待确认状态，执行启动自检和确认/回滚处理。

即使 Wi-Fi、MQTT、SNTP 或 SD 异常，BLE 扫描与生命周期管理仍保持运行；只是对应的绝对时间、CSV 或可靠重传能力降级。

## 7. 并发与资源设计

主要长期任务包括：

```text
nimble_host       NimBLE 主机
device_manager    生命周期判定与事件扇出
csv_logger        CSV 写入
storage_mgr       SD 挂载、故障恢复与状态管理
app_ui            UI 状态模型与 LVGL 更新
wifi_manager      Wi-Fi 重连
mqtt_service      MQTT 配置重载与 OTA 命令消费
publisher         Outbox、MQTT 发布、PUBACK、健康心跳
ota_manager       OTA 下载与切换
```

设计原则：

- 高吞吐事件队列优先放入 PSRAM：扫描、CSV、上传队列。
- 内部 DMA 内存保留给 Wi‑Fi、BLE、SD DMA、TLS 等必须使用内部内存的组件。
- 每个队列记录深度、高水位和丢弃计数。
- 每 30 秒采集扫描报告速率、过滤命中、回调耗时、队列等待时延、设备数量和投递丢失。
- `sys status`、`sys mem`、`sys tasks` 提供现场诊断证据。

整体上，这是一个以“**采集不中断、I/O 可隔离、数据可追溯、网络可恢复、故障可观测**”为核心目标的事件驱动网关架构。
