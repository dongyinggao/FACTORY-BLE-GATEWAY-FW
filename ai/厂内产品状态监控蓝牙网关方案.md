# 厂内产品状态监控蓝牙网关方案

## 1. 目标与范围

本方案定义 2026-08-07 可交付的“厂内产品状态监控蓝牙网关”现场试运行版本。网关部署在厂内指定区域，扫描目标产品的 BLE 广播，判定在线/离线状态，将状态变化记录到 microSD 的 CSV 文件，并通过厂内 Wi-Fi 使用 MQTT 上报事件。

## 2. 交付边界

### 本期完成

- CoreS3-SE 上的 LCD、Touch、BLE、Wi-Fi、microSD 基础功能。
- `ICD*`、`ICM*` 目标 BLE 设备的主动扫描与过滤。
- 设备名称、MAC、地址类型、RSSI、广播数据长度的采集。
- 设备在线、离线、重新在线状态判定；默认离线阈值 60 秒。
- microSD CSV 事件记录与断电后继续追加写入。
- Wi-Fi 自动连接/重连与 MQTT 状态事件上报。
- LCD 显示扫描状态、设备数量、在线数量和最近设备列表；Touch 启停扫描。
- 真实硬件上的扫描、记录、上传闭环演示与测试记录。

## 3. 硬件方案

| 项目 | 方案 | 作用 |
| --- | --- | --- |
| 主控 | M5Stack CoreS3-SE，ESP32-S3 | BLE 扫描、Wi-Fi、任务调度 |
| 交互 | 板载 LCD 与 Touch | 显示状态、扫描启停、现场诊断 |
| 本地记录 | microSD 卡，FATFS | 保存 CSV 状态事件，可读卡导出 |
| 配置保存 | 板载 Flash/NVS | 网关 ID、Wi-Fi 和 MQTT 参数 |
| 网络 | 2.4 GHz Wi-Fi | MQTT 上报 |
| 供电与部署 | USB-C 5 V 稳定电源、固定安装位置 | 支撑连续运行与 BLE 覆盖 |

现场安装应避免大型金属遮挡、强电磁源和不稳定供电；上线前通过 RSSI 和发现率确认安装位置。

## 4. 软件总体架构

```text
目标产品 BLE 广播 / Scan Response
             │
             ▼
BLE 扫描与过滤 ──► 设备状态管理 ──► CSV 存储（microSD）
             │                 │
             │                 ├──► LCD / Touch
             │                 │
             │                 └──► Wi-Fi / MQTT 上报
             │                                  │
             └──────────────────────────────────▼
                                             MQTT Broker
```

模块间使用 FreeRTOS 队列传递结构化事件。NimBLE 回调只生成扫描报告，不能操作 LVGL、SD 或 MQTT；UI、存储和网络分别作为消费者，避免慢速 I/O 阻塞扫描。

## 5. 模块设计

### 5.1 配置与时间模块

- NVS 保存网关 ID、Wi-Fi SSID/密码、MQTT Broker 地址/端口、MQTT Topic 和离线阈值。
- 首期允许通过编译配置或串口写入初始参数；LCD 只提供状态显示与扫描启停。
- 使用 SNTP 获取真实时间；校时未完成时，CSV 记录启动后的单调时间并标记时间未同步。

### 5.2 BLE 扫描与设备过滤模块

- 使用 ESP-IDF NimBLE 与 BLE-only 控制器。
- 扫描策略为 5 秒主动扫描会话；会话完成后立即启动下一轮。
- 主动扫描用于获取可能位于 Scan Response 中的设备名称。
- 解析名称、MAC、地址类型、RSSI 和原始广播数据；首期仅匹配名称前缀 `ICD*`、`ICM*`。
- 扫描启动失败或协议栈复位时显示错误并记录日志；本期采用有限次数、固定间隔的重试策略。

### 5.3 设备状态管理模块

设备管理器以 `MAC + 地址类型` 作为首期设备身份，维护设备名称、RSSI、最后发现时间和状态。若后续目标产品使用随机 MAC，再升级为厂商数据中的序列号或产品 ID。

```text
首次匹配广播 ──► Online ──超过 60 秒未发现──► Offline
                    ▲                              │
                    └────────再次发现──────────────┘
```

只有扫描器处于 `Scanning` 状态时，离线观察时间才累计。用户停止扫描、扫描错误或网关维护期间冻结计时，防止把“网关没有观察”误判为“产品离线”。

设备管理器发布 `DEVICE_ONLINE`、`DEVICE_OFFLINE`、`DEVICE_UPDATED` 和扫描状态事件，作为 CSV、MQTT 和 UI 的统一输入。

### 5.4 CSV 存储模块

- 使用 FATFS 挂载 microSD，启动时创建或打开当天/当前日志文件。
- 只追加状态变化事件；常规 RSSI 更新不逐条写入，避免日志膨胀。
- 推荐 CSV 字段：

```csv
timestamp,gateway_id,device_name,mac,address_type,event,rssi,online_duration_s
```

- 示例：

```csv
2026-08-07T10:20:30+08:00,GW-01,ICD001,AA:BB:CC:DD:EE:FF,1,OFFLINE,-55,3600
```

- 写入失败、SD 未挂载或剩余空间不足时，在 LCD 与串口显示错误；不影响 BLE 扫描和状态判定。
- 本期通过读卡器读取 CSV，不实现网关内日志浏览、文件轮转或自动清理。

### 5.5 Wi-Fi 与 MQTT 模块

- Wi-Fi 启动后使用 NVS 中的凭据连接厂内网络，断线后自动重连。
- MQTT 连接成功后上报新的状态变化事件；网络不可用时，事件仍保存在 SD CSV。
- 本期 MQTT 以“实时通知”为目标：不承诺历史事件自动补发或云端确认；CSV 用于人工追溯。
- 推荐 Topic：`factory/product-status/gateway/{gateway_id}/event`。
- 推荐 JSON：

```json
{
  "gateway_id": "GW-01",
  "device_name": "ICD001",
  "mac": "AA:BB:CC:DD:EE:FF",
  "event": "offline",
  "timestamp": "2026-08-07T10:20:30+08:00",
  "rssi": -55
}
```

若厂内 Broker 已支持 TLS，本期优先启用服务器证书校验；否则应明确隔离网络环境和凭据管理责任。

### 5.6 本地 UI 与诊断模块

LCD 首页显示：BLE 扫描状态、Wi-Fi/MQTT 连接状态、设备总数、在线数和最多四台最近设备。每行展示在线状态、名称、RSSI 和 MAC。

Touch 提供“开始扫描/停止扫描”控制。串口日志保留 NimBLE 同步、扫描启停、过滤命中、设备上线/离线、SD 状态、Wi-Fi/MQTT 状态和错误码，作为现场调试依据。

## 6. 任务与事件流

| 模块/任务 | 输入 | 输出 | 主要功能 |
| --- | --- | --- |
| BLE 扫描 | NimBLE GAP 回调 | 扫描报告队列 | 主动扫描、解析、名称过滤 |
| 设备管理 | 扫描报告、扫描状态 | 设备事件队列 | 去重、在线/离线判定 |
| CSV 存储 | 设备状态事件 | microSD CSV | 追加记录状态变化 |
| Wi-Fi/MQTT | 网络配置、设备状态事件 | MQTT Broker | 网络连接、实时上报 |
| UI | 扫描状态、设备状态、网络状态 | LCD/Touch | 本地展示与启停控制 |

15. 联调中发现的网关阻断性问题优先修复；服务端内部存储、查询页面和展示逻辑不纳入本项目代码交付。
16. 在真实现场或模拟现场演示“扫描 → 状态变化 → CSV → MQTT → 服务端融合”的闭环，并固化测试记录。

## 8. 测试与验收规划

### 8.1 无硬件测试

- 主机单元测试：名称过滤、设备去重、在线/离线计时、设备列表排序、容量边界。
- 固件构建：`idf.py build`。
- 构造扫描报告验证“扫描报告 → 设备状态事件 → CSV/MQTT 事件编码”的数据路径。

### 8.2 硬件集成测试

| 场景 | 验证点 |
| --- | --- |
| BLE 扫描 | ICD/ICM 设备被发现，名称、MAC、RSSI 正确显示和记录 |
| 离线判定 | 有效扫描累计 60 秒未发现后记录 `OFFLINE` |
| 暂停扫描 | 停止扫描超过 60 秒不产生错误离线事件 |
| SD | CSV 可追加、可用读卡器读取、字段完整 |
| Wi-Fi/MQTT | 网络连接后收到实时状态事件；断网不影响 SD 记录 |
| 服务端融合联调 | 按约定 Topic/JSON 接收消息；多网关重复观测可被识别、去重并保留来源网关 |
| 断电恢复 | 重启后重新扫描、恢复网络连接、继续写入 CSV |
| 多设备 | 多台 ICD/ICM 并发出现时状态与 LCD 列表正确 |

### 8.3 交付验收标准

- 可在指定区域持续扫描目标产品并显示设备状态。
- 目标设备上线、离线、重新在线均生成 CSV 记录。
- CSV 可从 SD 卡导出并被常见表格工具打开。
- Wi-Fi 可连接厂内网络，MQTT Broker 可收到实时状态事件。
- 在预留的服务端联调窗口内，服务端能够依据约定接口消费网关消息，并完成至少一组多网关融合验证。
- 停止扫描或网络断开不造成设备状态机异常；网络断开期间 CSV 仍可记录。
- 提供固件、烧录说明、配置样例、CSV 字段说明、MQTT 接口说明和测试记录。

## 9. 本期风险与前置条件

- 必须尽快获得真实 CoreS3-SE、microSD、目标 BLE 产品广播样例、厂内 Wi-Fi 凭据和可用 MQTT Broker。
- 如果目标产品使用随机 MAC，仅靠名称过滤会导致设备身份不稳定；应在方案冻结日确认是否存在稳定序列号或厂商数据。
- 如果厂内 Wi-Fi 需要复杂门户认证、企业证书或额外审批，应将网络接入风险单独处理，不纳入网关基础功能延期。
- MQTT 消息的服务端消费、持久化与可视化不属于本期交付范围；本期只保证网关按约定 Topic/JSON 实时发布，且 SD CSV 可人工追溯。

## 10. 方案设计评审待确认清单

以下事项应在 2026-07-27 的方案冻结评审中逐项结论化，并记录责任人与确认日期。

### 10.1 设备识别与扫描边界

1. 目标设备的最终身份字段是什么：设备名、`MAC + 地址类型`、厂商数据中的序列号，或产品 ID？若使用随机 MAC，必须提供稳定 ID。
2. `ICD*`、`ICM*` 是否为全部首期目标设备；是否存在需排除的同名前缀设备？
3. 广播间隔、设备数量、安装距离、金属遮挡和预期发现率分别是多少？
4. 单网关覆盖范围及多网关安装位置、网关 ID 和位置命名规则如何定义？

### 10.2 在线/离线诊断责任

1. 网关是否保留本地在线/离线状态机？建议保留，用于 LCD、CSV 和单网关现场诊断。
2. 多网关场景下，产品的全局在线/离线是否由服务端融合判定？建议由服务端判定：任一有效网关观测到设备即可作为全局在线依据。
3. 网关上传的事件语义是“本网关观测到/未观测到”，还是“产品全局上线/离线”？建议采用前者，并携带 `gateway_id`，避免多个网关互相产生矛盾状态。
4. 离线阈值是否固定为 60 秒；停扫、扫描错误、网关离线和 Wi-Fi 中断时是否冻结本地观察计时？

### 10.3 microSD 与 CSV 数据

1. 确认 SD 卡作为本期权威记录，并通过读卡器导出；在 SD 卡根目录创建 `data/` 保存 CSV，从而不开发上位机导出工具。
2. 确认文件组织：建议按天创建 `data/YYYYMMDD.csv`，当天文件追加写入；需要确认跨日、重启和文件名冲突的处理规则。
3. 确认最小字段：`timestamp`、`gateway_id`、`device_id`、`device_name`、`mac`、`address_type`、`event`、`rssi`、`online_duration_s`、`scanner_state`。
4. 确认事件范围：仅记录上线/离线/重新在线，还是同时记录扫描启停、SD 故障、Wi-Fi/MQTT 故障和设备 RSSI 更新。
5. 确认 CSV 编码（UTF-8）、时间格式（ISO 8601 +08:00）、表头写入规则、单文件容量上限、保留周期和 SD 满时的处理方式。

### 10.4 云端接口与融合规则

1. 确认 MQTT Broker 地址、端口、TLS 要求、认证方式、Topic 命名和 QoS。
2. 确认每条上报数据字段。建议至少包含：`event_id`、`timestamp`、`gateway_id`、`gateway_location`、`device_id`、`device_name`、`mac`、`event`、`rssi`、`observed_at`。
3. 确认事件唯一性与去重规则：建议键为 `gateway_id + event_id`；网关重启后的 `event_id` 规则也需明确。
4. 确认服务端融合窗口、全局离线阈值、重复观测处理和 RSSI 的用途；本期不以 RSSI 做定位结论。
5. 确认断网策略：本期网关仅实时 MQTT 上报、不做自动补发确认；SD CSV 保留人工追溯依据。

### 10.5 网络、时间与交付验证

1. 厂内 Wi-Fi 是否为 2.4 GHz、是否需要固定 IP、企业证书、MAC 白名单或门户认证？
2. SNTP 服务器、时区和未校时情况下的时间标记如何规定？
3. 网关 ID、安装位置、供电方式、SD 卡规格和现场标签由谁提供与维护？
4. 8 月 5–7 日服务端联调的联系人、Broker/测试环境、测试设备和验收样例是否已就绪？
5. 最终验收以哪些证据为准：CSV 文件、MQTT 报文、服务端融合结果、串口日志和现场演示录像。
