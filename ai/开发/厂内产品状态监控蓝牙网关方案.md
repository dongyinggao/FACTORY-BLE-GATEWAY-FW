# 厂内产品状态监控蓝牙网关方案

## 1. 目标与范围

本方案定义“厂内产品状态监控蓝牙网关”现场运行版本。一个房间可部署多台网关，以提高 BLE 广播发现概率。每台网关扫描目标产品的 BLE 广播、维护本地观测状态并记录到 microSD；通过厂内 Wi-Fi 使用 MQTT 上报观测与网关健康信息，由服务端融合为产品的全局状态。

## 2. 交付边界

### 本期完成

- CoreS3-SE 上的 LCD、Touch、BLE、Wi-Fi、microSD 基础功能。
- `ICD*`、`ICM*` 目标 BLE 设备的主动扫描与过滤。
- 设备名称、MAC、地址类型、RSSI、广播数据长度的采集。
- 设备本地在线、离线、重新在线状态判定；默认离线阈值 60 秒。
- microSD CSV 记录本地设备状态变化和网关关键事件，断电后继续追加写入。
- Wi-Fi 自动连接/重连，以及设备持续观测（`presence`）和网关健康心跳 MQTT 上报。
- 多网关场景下由服务端执行设备全局状态融合；本期不做 RSSI 定位。
- LCD 显示扫描状态、设备数量、在线数量和最近设备列表；Touch 启停扫描。
- 真实硬件上的扫描、记录、上传闭环演示与测试记录。

## 3. 硬件方案

| 项目 | 方案 | 作用 |
| --- | --- | --- |
| 主控 | M5Stack CoreS3-SE，ESP32-S3 | BLE 扫描、Wi-Fi、任务调度 |
| 交互 | 板载 LCD 与 Touch | 显示状态、扫描启停、现场诊断 |
| 本地记录 | microSD 卡，FATFS | 保存本地状态与网关事件 CSV，可读卡导出 |
| 配置保存 | 板载 Flash/NVS | 网关 ID、安装位置、Wi-Fi 和 MQTT 参数 |
| 网络 | 2.4 GHz Wi-Fi | MQTT 上报 |
| 供电与部署 | USB-C 5 V 稳定电源、固定安装位置 | 支撑连续运行与 BLE 覆盖 |


## 4. 软件总体架构

```text
目标产品 BLE 广播 / Scan Response
             │
             ▼
BLE 扫描与过滤 ──► 本地设备状态管理 ──► CSV 存储（microSD）
             │                 │
             │                 ├──► LCD / Touch
             │                 │
             │                 └──► Wi-Fi / MQTT 上报
             │                                  │
             └──────────────────────────────────▼
                                             MQTT Broker
                                                  │
                                                  ▼
                                      服务端多网关状态融合
```

模块间使用 FreeRTOS 队列传递结构化事件。NimBLE 回调只生成扫描报告，不能操作 LVGL、SD 或 MQTT；UI、存储和网络分别作为消费者，避免慢速 I/O 阻塞扫描。

## 5. 模块设计

### 5.1 配置与时间模块

- 使用 Flash 的 NVS 命名空间 `gateway_cfg` 保存配置。首期配置入口固定为 ESP-IDF 原生 `esp_console`：通过 CoreS3-SE 的 USB Serial/JTAG 提供串口 REPL，受限 `cfg` 命令调用配置模块写入 NVS。每台设备烧录相同固件后通过 USB 一次性配置；LCD 只显示配置和网络状态，不承担密码输入，microSD 仅保存日志、不作为配置来源。
- `esp_console` 已提供命令注册、参数解析、行编辑和 REPL，能与 ESP-IDF 5.5.5、USB Serial/JTAG 直接集成。启用交互输入时，配置 USB 控制台为 `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG`。
- NVS 配置项如下。`gateway_id` 在部署后必须唯一；`gateway_location` 和 `coverage_group` 用于服务端确定同一房间的网关覆盖组。

| 分类 | NVS 键 | 说明与示例 |
| --- | --- | --- |
| 网关身份 | `gateway_id` | 唯一标识，如 `GW-01` |
| 安装信息 | `gateway_location` | 位置，如 `Room101-North` |
| 安装信息 | `coverage_group` | 覆盖组，如 `Room101` |
| Wi-Fi | `wifi_ssid`、`wifi_password` | 厂内 2.4 GHz Wi-Fi 凭据 |
| MQTT | `mqtt_uri`、`mqtt_port` | 如 `mqtt://10.10.1.20`、`1883` |
| MQTT | `mqtt_username`、`mqtt_password`、`mqtt_qos` | 认证信息（可选）和 QoS，首期建议 QoS 1 |
| 业务参数 | `offline_threshold_s` | 本地离线阈值，默认 `60` 秒 |
| 时间 | `timezone`、`ntp_server` | 如 `Asia/Shanghai`、厂内 NTP 地址 |

- `cfg` 是白名单配置命令，不提供通用 NVS 读写 Shell。串口配置命令约定如下；`cfg commit` 校验必要字段后一次性写入 NVS，`cfg show` 必须隐藏 Wi-Fi 和 MQTT 密码。

```text
cfg set gateway_id GW-01
cfg set gateway_location Room101-North
cfg set coverage_group Room101
cfg set wifi_ssid Factory-IoT
cfg set wifi_password ********
cfg set mqtt_uri mqtt://10.10.1.20
cfg set mqtt_port 1883
cfg commit
cfg show
```

- 提供 `cfg factory-reset --confirm`，仅清除 `gateway_cfg` 命名空间并恢复未配置状态；不得擦除整片 Flash 或 microSD 数据。
- 启动时读取并校验 NVS：缺少 `gateway_id` 时显示“Gateway ID 未配置”，仍允许 BLE 扫描和 SD 日志；缺少 Wi-Fi/MQTT 参数时维持本地功能、网络显示“未配置”；配置完整后依次连接 Wi-Fi、SNTP 和 MQTT。配置或网络错误不得阻塞 BLE、UI 与 CSV。
- Wi-Fi/MQTT 密码不得由 `cfg show` 回显、写入串口日志或保存至命令历史；`cfg factory-reset` 必须要求显式确认。配置控制台运行在独立任务，不得阻塞 NimBLE、UI、SD 或 MQTT。
- 不将每台设备的 ID、位置或密码写入 `sdkconfig.defaults` 或提交至仓库，避免重复编译和凭据泄露。首期通过物理 USB 串口写入；后续批量部署时增加 PC 侧串口配置脚本，按配置表逐台发送同一组 `cfg` 命令并读取 `cfg show` 结果复核。
- 后续量产或大批量预配置可使用 ESP-IDF NVS Partition Generator，根据每台设备的 CSV 参数生成独立 NVS 分区镜像并烧录；本期不采用 SoftAP/BLE 手机配网、SD 配置文件或 MQTT 远程配置，以控制交付范围和 BLE 扫描共存风险。
- 使用 SNTP 获取真实时间；校时未完成时，CSV 记录启动后的单调时间并标记时间未同步。

### 5.2 BLE 扫描与设备过滤模块

- 使用 ESP-IDF NimBLE 与 BLE-only 控制器。
- 扫描策略为 5 秒主动扫描会话；会话完成后立即启动下一轮。
- 主动扫描用于获取可能位于 Scan Response 中的设备名称。
- 解析名称、MAC、地址类型、RSSI 和原始广播数据；首期仅匹配名称前缀 `ICD*`、`ICM*`。
- 扫描启动失败或协议栈复位时显示错误并记录日志；本期采用有限次数、固定间隔的重试策略。

### 5.3 设备状态管理模块

设备管理器维护的是“本网关的观测状态”，不对房间内产品的全局状态下结论。首期以 `MAC + 地址类型` 作为本地设备身份；MQTT 和 CSV 中统一使用 `device_id` 字段。若目标产品使用随机 MAC，方案冻结前必须提供广播厂商数据中的序列号或产品 ID 作为稳定 `device_id`。

```text
首次匹配广播 ──► Local Online ──超过 60 秒未发现──► Local Offline
                    ▲                              │
                    └────────再次发现──────────────┘
```

只有扫描器处于 `Scanning` 状态时，离线观察时间才累计。用户停止扫描、扫描错误或网关维护期间冻结计时，防止把“网关没有观察”误判为“产品离线”。

设备管理器发布 `LOCAL_ONLINE`、`LOCAL_OFFLINE`、`DEVICE_UPDATED` 和扫描状态事件，作为 CSV、UI 及 MQTT 观测聚合的统一输入。`LOCAL_OFFLINE` 仅表示“该网关持续有效扫描后未再观察到设备”，不能等同于产品全局离线。本地上线、离线和重新在线均用于 LCD、串口及 CSV 诊断记录；首期 MQTT 不上传 `LOCAL_ONLINE` 或 `LOCAL_OFFLINE` 结论。

#### Note:
当前方案中：

- 网关持续处于 `SCANNING` 时，某设备超过 60 秒未被本机再次发现，网关产生 `LOCAL_OFFLINE`。
- `LOCAL_OFFLINE` 用于本地 LCD、串口诊断和 SD 卡 CSV 记录。
- 它不等同于“产品全局离线”，因为同一房间内其他网关可能仍能看到该设备。

首期 MQTT **不上传 `LOCAL_OFFLINE` 结果**。网关仅上传：

- `presence`：本机仍观察到设备；
- `gateway_health`：本机是否正常扫描、网络和时间是否正常。

服务器据此融合判断：

- 任一健康网关近期有 `presence` → 全局 `ONLINE`
- 覆盖组中所有健康网关均超过阈值未见到设备 → 全局 `OFFLINE`
- 覆盖组网关整体不可用、停扫或异常 → `UNKNOWN`

这样可避免一台网关因遮挡、故障或停扫而误报全局离线。

### 5.4 CSV 存储模块

- 使用 FATFS 挂载 microSD，在根目录 `data/` 下创建或打开当天文件 `YYYYMMDD.csv`。
- SD 卡只追加两类关键记录：本地设备状态变化和网关关键事件。常规 RSSI 更新、每个 BLE 广播包及 MQTT 重传均不逐条写入，避免日志膨胀。
- 本地设备状态变化仅在状态切换时记录：首次观察到设备记录 `LOCAL_ONLINE`；设备从 `LOCAL_OFFLINE` 后再次被观察到也记录 `LOCAL_ONLINE`；扫描器持续处于 `SCANNING` 且超过离线阈值未再观察到设备时记录 `LOCAL_OFFLINE`。
- 设备状态记录字段：

```csv
timestamp,gateway_id,gateway_location,device_id,device_name,mac,address_type,event,last_seen_at,rssi,online_duration_s,scanner_state
```

CSV 设备状态记录字段
| 字段 | 含义 |
| --- | --- |
| `timestamp` | 本条 CSV 事件写入时间，使用 SNTP 校时后的 ISO 8601 时间。 |
| `gateway_id` | 产生记录的唯一网关编号，如 `GW-01`。 |
| `gateway_location` | 网关实际安装位置，如 `Room101-North`。 |
| `device_id` | 设备稳定身份。优先为厂商数据中的序列号/产品 ID；首期没有时可由 `MAC + address_type` 表示。 |
| `device_name` | BLE 广播名称，用于现场识别和展示，如 `ICD001`。不能单独作为正式唯一身份。 |
| `mac` | 本次观测到的 BLE MAC 地址。 |
| `address_type` | BLE 地址类型，用于和 MAC 共同构成首期本地去重键。 |
| `event` | 本地状态事件，如 `LOCAL_ONLINE`、`LOCAL_OFFLINE`；网关关键事件时也可填写扫描、SD 或网络相关事件类型。 |
| `last_seen_at` | 最后一次实际接收到该设备 BLE 广播的时间；离线记录时尤其重要。 |
| `rssi` | 最后一次或状态切换时的信号强度，单位 dBm。仅作诊断，不作首期定位结论。 |
| `online_duration_s` | 本次由本网关观察到设备处于本地在线状态的累计时长，单位秒。首次上线为 `0`。 |
| `scanner_state` | 写入事件时的扫描器状态，如 `SCANNING`、`IDLE`、`ERROR`；离线记录应为 `SCANNING`。 |


- 示例：

```csv
2026-08-07T10:01:22+08:00,GW-01,Room101-North,ICD001,ICD001,AA:BB:CC:DD:EE:FF,1,LOCAL_ONLINE,2026-08-07T10:01:22+08:00,-55,0,SCANNING
2026-08-07T11:12:35+08:00,GW-01,Room101-North,ICD001,ICD001,AA:BB:CC:DD:EE:FF,1,LOCAL_OFFLINE,2026-08-07T11:11:35+08:00,-70,4263,SCANNING
```

- `device_id` 是正式设备身份，优先使用广播厂商数据中的序列号或产品 ID；暂时没有稳定 ID 时使用 `MAC + 地址类型`。
- `timestamp` 是本条记录写入时间，`last_seen_at` 是最后实际收到该设备广播的时间；`online_duration_s` 是本次由本网关观察到的在线时长；`scanner_state` 用于证明离线判断时网关确实处于扫描状态。
- 网关关键事件至少记录：固件启动/重启、扫描开始/停止/错误、NimBLE 重置、SD 挂载或写入错误、Wi-Fi/MQTT 连接变化和 SNTP 校时成功/失败。可与设备状态写入同一当天 CSV，设备字段不适用时留空；若后续日志量增大，再拆分为 `gateway_events.csv`。
- 如现场需要排查 RSSI，可选地增加“每设备每分钟一条”的聚合观测记录（例如窗口内 RSSI 中位数、最大值和最后观测时间）；不保存逐条 BLE 广播包。
- 写入失败、SD 未挂载或剩余空间不足时，在 LCD 与串口显示错误；不影响 BLE 扫描和状态判定。
- 本期通过读卡器读取 CSV，不实现网关内日志浏览、文件轮转或自动清理。

### 5.5 Wi-Fi 与 MQTT 模块

- Wi-Fi 启动后使用 NVS 中的凭据连接厂内网络，断线后自动重连。
- MQTT 连接成功后上报两类最小消息：设备持续观测 `presence` 与网关健康心跳 `gateway_health`；网络不可用时，本地 CSV 仍持续记录。
- 本期 MQTT 以“实时通知”为目标：不承诺历史事件自动补发或云端确认；CSV 用于人工追溯。
- 推荐 Topic：

```text
factory/product-status/gateway/{gateway_id}/presence
factory/product-status/gateway/{gateway_id}/health
```

- `presence` 对每个已发现设备每 15～30 秒最多发送一次，表示本网关在该时间窗口内仍观察到该设备；RSSI 使用窗口中位数或最后一次值，首期不据此做定位。
- `gateway_health` 每 30 秒发送一次，表示网关是否仍在有效扫描、网络是否可用、时间是否已同步。
- 不上报 `LOCAL_ONLINE`、`LOCAL_OFFLINE` 或“产品全局上线/离线”结论；本机未观察到设备时停止发送该设备的 `presence`，由服务端结合覆盖组内其余网关的 `presence` 和 `gateway_health` 判断全局状态。
- 每条消息包含单网关唯一的 `event_id`，服务端以 `gateway_id + event_id` 去除 QoS 1 的重复投递。建议 JSON 如下：

```json
{
  "schema_version": 1,
  "event_id": "GW-01-20260807-000123",
  "event_type": "presence",
  "timestamp": "2026-08-07T10:20:30+08:00",
  "gateway_id": "GW-01",
  "gateway_location": "Room101-North",
  "device_id": "ICD001",
  "device_name": "ICD001",
  "mac": "AA:BB:CC:DD:EE:FF",
  "address_type": 1,
  "observed_at": "2026-08-07T10:20:22+08:00",
  "rssi_median": -55,
  "scanner_state": "SCANNING"
}
```
MQTT presence JSON 字段
| 字段 | 含义 |
| --- | --- |
| `schema_version` | 消息格式版本，首期固定为 `1`，后续协议升级时用于兼容解析。 |
| `event_id` | 单台网关内唯一的消息编号。服务端以 `gateway_id + event_id` 去重。 |
| `event_type` | 消息类型；该示例固定为 `presence`，表示本网关近期仍看到该设备。 |
| `timestamp` | 网关生成并发送本消息的时间。 |
| `gateway_id` | 发送消息的唯一网关编号。 |
| `gateway_location` | 发送网关的安装位置，用于服务端确定覆盖组与观测来源。 |
| `device_id` | 设备稳定身份，是服务端融合多网关观测的主键。 |
| `device_name` | BLE 广播设备名，用于展示和诊断。 |
| `mac` | 本网关本次观测到的 BLE MAC 地址。 |
| `address_type` | BLE 地址类型；与 MAC 配合用于首期身份追溯。 |
| `observed_at` | 本网关最后实际看到设备广播的时间。服务端应主要依据此时间判断观测是否新鲜。 |
| `rssi_median` | 本次上报窗口内 RSSI 的中位数，单位 dBm，减少单次波动影响。 |
| `scanner_state` | 发送观测时的扫描状态，正常应为 `SCANNING`。 |

```json
{
  "schema_version": 1,
  "event_id": "GW-01-20260807-000124",
  "event_type": "gateway_health",
  "timestamp": "2026-08-07T10:21:00+08:00",
  "gateway_id": "GW-01",
  "gateway_location": "Room101-North",
  "scanner_state": "SCANNING",
  "wifi_state": "CONNECTED",
  "mqtt_state": "CONNECTED",
  "time_synced": true,
  "uptime_s": 7200
}
```
MQTT gateway_health JSON 字段
| 字段 | 含义 |
| --- | --- |
| `schema_version`、`event_id`、`timestamp`、`gateway_id`、`gateway_location` | 含义同 `presence` 消息。 |
| `event_type` | 固定为 `gateway_health`，表示网关健康心跳。 |
| `scanner_state` | BLE 扫描器状态，用于判断网关是否具备有效观测能力。 |
| `wifi_state` | Wi‑Fi 状态，如 `CONNECTED`、`DISCONNECTED`。 |
| `mqtt_state` | MQTT 状态，如 `CONNECTED`、`DISCONNECTED`。 |
| `time_synced` | 是否已完成 SNTP 校时；为 `false` 时，服务端应谨慎使用绝对时间。 |
| `uptime_s` | 本次启动后持续运行时间，单位秒；可辅助判断重启和运行稳定性。 |


- 服务端融合规则：任一健康且处于 `SCANNING` 的网关在 60 秒内收到该设备 `presence`，则设备全局状态为 `ONLINE`；设备所属房间/覆盖组内全部健康网关均超过 60 秒未收到时才为 `OFFLINE`；该覆盖组网关均失联、停扫或扫描异常时为 `UNKNOWN`，不得误判为 `OFFLINE`。服务端按 `gateway_location` 配置网关所属覆盖组，保留各网关来源与最近 RSSI，但不把多台网关的同一设备观测视为多次上线。

若厂内 Broker 已支持 TLS，本期优先启用服务器证书校验；否则应明确隔离网络环境和凭据管理责任。

### 5.6 本地 UI 与诊断模块

LCD 首页显示：BLE 扫描状态、Wi-Fi/MQTT 连接状态、设备总数、在线数和最多四台最近设备。每行展示在线状态、名称、RSSI 和 MAC。

Touch 提供“开始扫描/停止扫描”控制。串口日志保留 NimBLE 同步、扫描启停、过滤命中、设备上线/离线、SD 状态、Wi-Fi/MQTT 状态和错误码，作为现场调试依据。

## 6. 任务与事件流

| 模块/任务 | 输入 | 输出 | 主要功能 |
| --- | --- | --- |
| BLE 扫描 | NimBLE GAP 回调 | 扫描报告队列 | 主动扫描、解析、名称过滤 |
| 设备管理 | 扫描报告、扫描状态 | 本地设备事件队列 | 去重、本地在线/离线判定、观测聚合 |
| CSV 存储 | 本地设备事件、网关关键事件 | microSD CSV | 追加本地状态变化与诊断事件 |
| Wi-Fi/MQTT | 网络配置、观测聚合、网关状态 | MQTT Broker | 网络连接、`presence` 与健康心跳上报 |
| UI | 扫描状态、设备状态、网络状态 | LCD/Touch | 本地展示与启停控制 |

## 8. 测试与验收规划

### 8.1 无硬件测试

- 主机单元测试：名称过滤、设备去重、在线/离线计时、设备列表排序、容量边界。
- 固件构建：`idf.py build`。
- 构造扫描报告验证“扫描报告 → 本地状态事件 → CSV / presence 编码”的数据路径；构造健康状态验证 `gateway_health` 编码。

### 8.2 硬件集成测试

| 场景 | 验证点 |
| --- | --- |
| BLE 扫描 | ICD/ICM 设备被发现，名称、MAC、RSSI 正确显示和记录 |
| 离线判定 | 有效扫描累计 60 秒未发现后记录 `LOCAL_OFFLINE` |
| 暂停扫描 | 停止扫描超过 60 秒不产生错误 `LOCAL_OFFLINE` 事件 |
| SD | CSV 可追加、可用读卡器读取、字段完整 |
| NVS 配置 | USB Serial/JTAG 的 `esp_console` 可执行 `cfg` 命令；串口配置后重启仍保留；`cfg show` 与命令历史不泄露密码；缺少网络配置时本地扫描与 CSV 仍可运行 |
| Wi-Fi/MQTT | 网络连接后收到 `presence` 和 `gateway_health`；断网不影响 SD 记录 |
| 服务端融合联调 | 多网关重复观测可保留来源并融合；覆盖组中任一健康网关最近观测为全局 `ONLINE`，覆盖组整体不可用时为 `UNKNOWN` |
| 断电恢复 | 重启后重新扫描、恢复网络连接、继续写入 CSV |
| 多设备 | 多台 ICD/ICM 并发出现时状态与 LCD 列表正确 |

### 8.3 交付验收标准

- 可在指定区域持续扫描目标产品并显示设备状态。
- 目标设备本地上线、离线、重新在线均生成 CSV 记录，并包含网关身份和最后观测时间。
- CSV 可从 SD 卡导出并被常见表格工具打开。
- Wi-Fi 可连接厂内网络，MQTT Broker 可收到 `presence` 和 `gateway_health`。
- 每台网关可通过串口写入唯一 ID、位置、覆盖组和网络参数，重启后配置保持有效。
- 在预留的服务端联调窗口内，服务端能够依据约定接口消费网关消息，完成至少一组多网关 `ONLINE / OFFLINE / UNKNOWN` 融合验证。
- 停止扫描或网络断开不造成设备状态机异常；网络断开期间 CSV 仍可记录。
- 提供固件、烧录说明、配置样例、CSV 字段说明、MQTT 接口说明和测试记录。

## 9. 本期风险与前置条件

- 必须尽快获得真实 CoreS3-SE、microSD、目标 BLE 产品广播样例、厂内 Wi-Fi 凭据和可用 MQTT Broker。
- 如果目标产品使用随机 MAC，仅靠名称过滤会导致设备身份不稳定；应在方案冻结日确认是否存在稳定序列号或厂商数据。
- 如果厂内 Wi-Fi 需要复杂门户认证、企业证书或额外审批，应将网络接入风险单独处理，不纳入网关基础功能延期。
- MQTT 消息的服务端消费、持久化与可视化不属于本项目代码交付范围；本期网关保证按约定 Topic/JSON 实时发布 `presence` 和健康心跳，SD CSV 可人工追溯。
- SoftAP/BLE 手机配网、SD 配置文件、MQTT 远程配置和 NVS 参数预烧录不属于首期交付；若后续批量部署，再采用 PC 串口脚本或 NVS 分区镜像生成工具。

## 10. 方案设计评审待确认清单

以下事项应在 2026-07-27 的方案冻结评审中逐项结论化，并记录责任人与确认日期。

### 10.1 设备识别与扫描边界

1. 目标设备的最终身份字段是什么：设备名、`MAC + 地址类型`、厂商数据中的序列号，或产品 ID？若使用随机 MAC，必须提供稳定 ID。
2. `ICD*`、`ICM*` 是否为全部首期目标设备；是否存在需排除的同名前缀设备？
3. 广播间隔是多少？
4. 单网关覆盖范围及多网关安装位置、网关 ID 和位置命名规则如何定义？

### 10.2 在线/离线诊断

1. 网关保留本地在线/离线状态机，用于 LCD、CSV 和单网关现场诊断；其事件命名固定为 `LOCAL_ONLINE`、`LOCAL_OFFLINE`。
2. 产品全局状态由服务端融合：任一健康且有效扫描的覆盖组网关在 60 秒内有 `presence` 为 `ONLINE`；该覆盖组全部健康网关超时才为 `OFFLINE`；覆盖组整体不可用时为 `UNKNOWN`。
3. 网关 MQTT 首期仅发送 `presence` 与 `gateway_health`，不发送“产品全局上线/离线”结论；本地状态变化仅写 SD 和本地诊断日志。
4. 离线阈值固定为 60 秒；停扫、扫描错误或网关维护时冻结本地观察计时。Wi-Fi/MQTT 中断不影响本地扫描与 CSV 记录。

### 10.3 microSD 与 CSV 数据

1. 确认 SD 卡记录数据，并通过读卡器导出；在 SD 卡根目录创建 `data/` 保存 CSV，从而不开发上位机导出工具。
2. 确认文件组织：建议按天创建 `data/YYYYMMDD.csv`，当天文件追加写入；需要确认跨日、重启和文件名冲突的处理规则。
3. 确认最小设备记录字段：`timestamp`、`gateway_id`、`gateway_location`、`device_id`、`device_name`、`mac`、`address_type`、`event`、`last_seen_at`、`rssi`、`online_duration_s`、`scanner_state`。
4. 本期固定记录 `LOCAL_ONLINE`、`LOCAL_OFFLINE` 及网关关键事件；不记录逐条广播、常规 RSSI 更新或 MQTT 重传。
5. 确认 CSV 编码（UTF-8）、时间格式（ISO 8601 +08:00）、表头写入规则、单文件容量上限、保留周期和 SD 满时的处理方式。

### 10.4 云端接口与融合规则

1. 确认 MQTT Broker 地址、端口、TLS 要求、认证方式、Topic 命名和 QoS。
2. 固定上报两类消息：`presence` 与 `gateway_health`；确认第 5.5 节 JSON 字段、Topic、频率和 QoS。
3. 确认事件唯一性与去重规则：服务端以 `gateway_id + event_id` 去重；网关重启后的 `event_id` 规则也需明确。
4. 确认服务端融合窗口、全局离线阈值与 `UNKNOWN` 条件；多网关重复观测保留来源，本期不以 RSSI 做定位结论。
5. 确认断网策略：本期网关仅实时 MQTT 上报、不做自动补发确认；SD CSV 保留人工追溯依据。

### 10.5 网络、时间与交付验证

1. 厂内 Wi-Fi 是否为 2.4 GHz、是否需要固定 IP、企业证书、MAC 白名单或门户认证？
2. SNTP 服务器、时区和未校时情况下的时间标记如何规定？
3. 网关 ID、安装位置、覆盖组、供电方式、SD 卡规格和现场标签由谁提供与维护？串口配置人员、配置表和 `cfg show` 复核流程如何确定？
4. 8 月 5–7 日服务端联调的联系人、Broker/测试环境、测试设备和验收样例是否已就绪？
5. 最终验收以哪些证据为准：CSV 文件、MQTT 报文、服务端融合结果？
