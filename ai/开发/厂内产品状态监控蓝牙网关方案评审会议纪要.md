# 厂内产品状态监控蓝牙网关方案评审会议纪要

## 主题

本会议由研发软件、质量和生产共同评审“厂内产品状态监控蓝牙网关方案”，重点确认数据可靠性、设备广播生命周期、容量、OTA 与配置管理的交付边界。

## 时间

2026-07-27

## 目的

明确网关侧数据记录和 MQTT 上报策略，识别量产与现场运行风险，确认后续方案和开发需要补充的功能及验证项。

## 会议内容与结论

### 1. MQTT 断网重连与中断数据重传

现有“仅实时上报、不补发”的设计不能满足断网期间数据完整性要求。会议决定增加**持久化上报队列（Outbox）**：

- 每条待上传消息包含稳定的 `event_id`；服务端仍以 `gateway_id + event_id` 去重。
- MQTT 不可用时，消息先写入 SD 卡 `outbox/` 持久化队列；网络和 MQTT 恢复后按文件顺序重传。
- MQTT 采用 QoS 1；首期以 Broker `PUBACK` 作为网关侧删除 Outbox 记录的条件。服务端使用固定 Client ID、持久会话、QoS 1 消费，并按 `gateway_id + event_id` 去重。
- Outbox 与人工可读 CSV 的职责分离：CSV 用于追溯，Outbox 用于可靠重传。Outbox 采用 256 KiB 追加式分段文件，默认上限 256 MiB；断电后允许尾部消息重传。

### 2. SD 卡读写寿命

会议要求评估 SD 卡写入寿命，避免逐条 BLE 广播或频繁 RSSI 更新写入造成过度磨损。

- CSV 继续仅记录广播开始、广播结束及网关关键事件，不记录逐条广播包。
- Outbox 应采用批量追加、按文件顺序确认删除或轮转的方式，避免每条消息随机改写同一扇区。
- 推荐使用容量至少 2 GiB、优先工业级 16 GiB 及以上 SD 卡；软件侧需要统计每日写入量、单条记录大小、预计写入次数和容量增长，并给出预留空间、满卡与写入失败处理策略。
- 质量侧需安排长时间写入、断电恢复、满卡和读卡导出测试。

### 3. 扫描设备数量上限

首期网关本地设备表容量暂定为 **128 台**。

- 软件需要将设备表、设备列表、观测聚合、CSV/MQTT 队列容量按 128 台目标设计。
- UI 只显示最近或优先级最高的少量设备，不以 LCD 行数限制设备表容量。
- 需要完成 128 台设备的内存占用、队列满载、重复广播、高频状态切换和持续运行测试；超过容量时必须有明确的丢弃策略和日志。

### 4. 在线 OTA

会议要求纳入在线 OTA 能力。

- 使用 ESP-IDF 双 OTA 分区进行 HTTPS 固件下载、镜像完整性/SHA-256 校验、切换启动与失败回滚。
- OTA 状态（可用版本、下载、校验、切换、失败原因）需要在 LCD、串口和 CSV 网关事件中可追溯。
- OTA 期间应暂停或受控停止 BLE 扫描，并在升级成功重启后恢复扫描、网络连接和本地记录。
- OTA 镜像来源、TLS/证书校验、版本发布、灰度范围和回滚验收流程需与质量、生产共同确认。

### 5. 设备名称过滤可扩展

已确认首期目标设备名称为不区分大小写的 `SM_ICM数字`、`SM_ICD数字`，例如 `SM_iCM2`、`SM_ICM2`。会议要求在保持默认规则的基础上支持可扩展的目标设备名称规则。

- 首期至少支持多个名称规则的 NVS 白名单配置，并内置 `SM_ICM数字`、`SM_ICD数字` 的不区分大小写默认规则。
- 过滤规则应可通过 NVS 配置读取；后续可通过 OTA 引入新增默认规则或配置格式迁移。
- 需要限制规则数量和单条长度，避免超出 NVS、内存与广播解析边界。

### 6. 配置功能与 OTA 的协同

会议要求 OTA 中尽可能包含配置能力。

- 配置管理模块、NVS 配置校验、配置版本号、默认值和迁移逻辑必须随固件 OTA 一并交付。
- 常规固件 OTA 不覆盖现场已配置的网关 ID、位置、Wi-Fi、MQTT 等 NVS 参数；仅在配置版本升级且存在新增字段时补充默认值或执行受控迁移。
- 如需集中修改现场参数，应另行定义经鉴权的配置下发机制；不将其与普通固件 OTA 混为同一操作。
- USB Serial/JTAG 的 `esp_console` 与 `cfg` 命令仍是首期现场配置入口。

### 7. 设备广播生命周期定义

会议确认原“设备上线/下线”的描述不够准确，后续统一改为“**设备广播开始/广播结束**”。

- 网关首次收到某设备本轮广播包时，记录 `BROADCAST_STARTED`，其时间为首次接收广播包的时间。
- 网关在广播结束判定超时前收到的最后一个广播包时间记录为 `last_seen_at`，并作为 `BROADCAST_ENDED` 的广播结束时间。
- 网关实际生成 `BROADCAST_ENDED` 事件的时间晚于 `last_seen_at`，两者必须分别保留，不能把判定时间误写为广播结束时间。
- 已确认目标设备 MAC 地址唯一且固定；首期以 MAC 作为 `device_id`，BLE 地址类型仅作协议追溯。
- 正常场景中，单轮广播通常持续约 20～30 秒后结束；异常场景可能出现多次频繁的“开始—结束”循环。
- 广播结束判定超时作为可配置项 `bcast_end_s`，首期默认 60 秒、允许范围 5～300 秒；后续依据真实设备广播间隔和现场丢包情况调整，且不将其误写为广播结束时间。
- MQTT 上报 `broadcast` 和 `gateway_health`，不上传设备在线/离线或产品全局状态结论；单网关 `BROADCAST_ENDED` 作为采集事件可靠上报。

## 方案影响

1. 设备状态机、CSV 事件名、UI 文案和测试用例需由 `LOCAL_ONLINE/LOCAL_OFFLINE` 调整为 `BROADCAST_STARTED/BROADCAST_ENDED`。
2. CSV 需要同时保留广播开始时间、最后广播包时间和结束判定生成时间。
3. MQTT 模块增加持久化 Outbox、重传和去重验证；服务端需支持重复消息去重。
4. 原 128 台容量目标、OTA、可扩展名称规则和配置版本迁移均增加了内存、存储和回归测试工作量。
